# UPS 2025 Annual Shipping Performance — Executive Dashboard

An end-to-end Power BI build: source-to-star-schema ETL, a full DAX measure library, a
Power Query implementation that refreshes straight from the raw extracts, page and
interaction specifications, and a working HTML executive dashboard that renders the
same measures for validation and circulation.

Built from the *UPS 2025 Annual Power BI Dashboard Build Guide v2* against four real
monthly UPS billing extracts.

---

## Quick start

```bash
pip install -r etl/requirements.txt

# 1. Transform raw UPS extracts into the star schema (real data, stays local)
python etl/ups_etl.py --raw data/raw --out data/processed --report

# 2. Build the executive dashboard from those results
python dashboard/build_dashboard.py --data data/processed --out dashboard/live.html

# Or run the whole thing on the committed synthetic sample
python etl/make_sample_data.py --out data/sample
python dashboard/build_dashboard.py --data data/sample --out dashboard/index.html
```

Open `dashboard/index.html` in a browser. It is self-contained — no build step, no
network, no licence.

---

## A note on the data in this repository

`data/raw/` and `data/processed/` are **git-ignored**. The source extracts contain a
named client's account numbers, shipping addresses and negotiated spend, which does not
belong in a repository.

What ships instead is `data/sample/` — a clearly-labelled synthetic set generated by
`etl/make_sample_data.py` with a fixed seed. Same schema, realistic *shapes*
(dominant ground service, a heavy-vs-light weight split, one account carrying
disproportionate loss claims), invented values. It lets anyone clone this repo and get
a working dashboard in two commands.

To work with real data: drop the extracts into `data/raw/` and run the two commands
above. Everything downstream is identical.

## What this build adds to the original guide

The guide specifies the pages, the KPI list and the scoring weights. Seven things were
needed to make it actually work against the real extracts.

**1. The year-to-date double-count.** The February file is a YTD extract containing
January *and* February. The January file contains January. A `Get Data → Folder` append
— the approach the guide describes — double-counts January exactly: a **100%**
overstatement of that month, ~40% of the loaded period, with no error and a total that
still looks plausible. The load deduplicates on month/account/product with single-period
files taking precedence, and reports the 161 suppressed rows.

**2. The two source vocabularies.** Volume & Net Spend calls a service
`NDA REG / EXPRESS PKG`; Time-in-Transit calls the same service `NEXT DAY AIR`. Neither
list is a subset of the other. Without a conformed bridge there is no way to put cost
and reliability for one service on one row, and the recommendation is impossible.
`Dim_ServiceMapping` is keyed on `(SourceSystem, RawProduct)` for exactly this.

**3. The scoring arithmetic.** The guide gives four weights across four different units,
three "higher is better" and one "lower is better". Added: min-max normalisation across
the qualified set, per-metric direction, and **weight reallocation** — a component that
cannot be measured has its weight redistributed rather than scored as zero.

**4. Cost must be weight-normalised.** Ground averages 16.1 lb per piece against 2.3 lb
for 2nd Day Air. Per shipment they cost within $0.36 of each other; per billed pound
Ground is **7.3× cheaper**. Scoring on cost-per-shipment — as the guide specifies —
would make migrating Ground volume to air look nearly free. Both views appear on the
report; the score uses the per-pound one.

**5. Claims cannot be attributed to a service.** The claims export has no product,
service or tracking key, so 50% of the scoring weight is unallocatable at service grain.
The model deliberately has *no relationship* from claims to service — a service slicer
visibly does nothing on that page — and the score reports its own effective weights
wherever it appears.

**6. Statistical confidence, not just a volume floor.** A hard threshold answers "is
this big enough to rank?" but not "how much of this number is real?". Ranking uses the
**Wilson score interval lower bound**, so thin samples fall down the list in proportion
to how little is known about them. Next Day Air Early: 4 packages measured, 100% on
time, confidence floor **51%**.

**7. Accessorial detail.** Not in the guide's data model. It is the only source that
explains *why* cost per piece moves, and it surfaces $10,272/month of Address Correction
charges — packages sent to bad addresses the firm supplied, fully avoidable, ~$123k
annualised.

## Headline findings

From the real extracts: Jan–Apr 2025 volume and spend, March 2025 transit and claims.

| | |
|---|---|
| Shipments | 293,921 |
| Net spend | $4,519,934 |
| On-time delivery (March) | 96.46% across 67,091 measured packages |
| Of late packages, missed the **day** | **95.9%** |
| Loss claims | 5.1 per 10,000 |
| **Loss claim concentration** | **One account = 80% of all loss claims, 4.4× firm rate** |
| Best qualified service | 2nd Day Air / Expedited, 98.23% |
| Volume anchor | Ground, 72% of volume at $0.89/lb |

Full detail and the recommendation: [`docs/02_executive_summary.md`](docs/02_executive_summary.md).

**Reporting basis is PROVISIONAL.** One month of transit and claims data cannot separate
a consistently reliable service from one having a good month. Cost conclusions are
solid; service reliability conclusions are directional until at least six completed
months are loaded.

## Validation

The ETL and the dashboard cross-check against the source in four independent ways:

| Check | Result |
|---|---|
| January volume vs source extract | 79,359 — exact |
| On-time delivery vs source Grand Total row | 96.46% vs 0.9646 — exact |
| Accessorial detail vs Volume & Spend net spend (March) | $1,053,748.13 both — exact |
| Shipper View measured vs Payor View billed | 97.9% — expected population gap |

Any disagreement between the HTML dashboard and the Power BI model is a real defect in
one of them. That is the point of building both.
